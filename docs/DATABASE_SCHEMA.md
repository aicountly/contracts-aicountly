# Database schema

PostgreSQL 14+. 64 tables across 13 migrations, applied in filename order by
`database/migrate.php`.

```bash
php database/migrate.php            # apply everything pending
php database/migrate.php --status   # list applied and pending, change nothing
php database/migrate.php --seed     # also apply database/seeds/*.sql (dev only)
```

Each file runs inside **one transaction**, so a migration either lands whole or
not at all — a half-applied schema is not a state this product can reach.
Applied files are recorded in `contracts_migration`, which is what makes
re-running safe.

## Conventions

| Convention | Why |
|---|---|
| `BIGINT GENERATED BY DEFAULT AS IDENTITY` primary keys | |
| A `UUID` on anything a URL or another product may reference | A sequential id in a URL is an enumeration hint |
| `(environment, cmp_id)` on every tenant-owned table | `environment` looks redundant while each deployment has its own database, and stops being redundant the first time a production dump is restored into sandbox |
| Bare `TIMESTAMP` holding UTC | The connection pins `SET TIME ZONE 'UTC'`, so every stored instant means one thing on every host |
| `NUMERIC` for money, carried as a **string** end to end | A contract value that has been through a JavaScript float is a value you cannot reconcile |
| Statuses as `CHECK` constraints matching `Support\Enums` | The two change together, and a migration makes that visible in review |
| `JSONB` only for open-ended metadata | Anything filtered, summed or sorted gets a real column |
| Soft delete (`archived_at`) only where history matters | A draft is deleted; an executed contract is archived |

## `contracts` — the central table

Beyond the obvious fields, four are worth explaining.

**`notice_deadline`** is stored, not computed. It is `expiry_date -
notice_period_days`, and the nightly sweep filters on it across every tenant. An
index on a stored column is the difference between a range seek and a full scan.

**`counterparty_name`** is denormalised from the primary party so the repository
list renders without a join or a Contacts round trip per row.

**`parent_contract_id`** is the amendment chain. A child points at its master;
the master is never rewritten, which is what makes "what did we actually agree
to" answerable at any point in time.

**`search_vector`** is maintained by a trigger, not by application code. Any
write path that forgot to call an update function would leave a contract
unsearchable, and there are many write paths.

### Constraints that carry real meaning

```sql
CHECK (expiry_date IS NULL OR effective_date IS NULL OR expiry_date >= effective_date)
```
A contract that expires before it starts is a data-entry slip that would
otherwise surface months later as a renewal that never fires.

```sql
CHECK (currency ~ '^[A-Z]{3}$')
CHECK (ai_risk_score IS NULL OR ai_risk_score BETWEEN 0 AND 100)
CHECK (parent_contract_id IS NULL OR parent_contract_id <> id)
UNIQUE (environment, cmp_id, contract_number)
```

Contract numbers are unique **per company** — two companies both starting at
`CON-2026-000001` is correct, and a global unique constraint would be wrong.

## Numbering

`contract_number_counters` rather than a sequence, because numbering is per
company and optionally resets each year, and one shared sequence can do neither.
Allocation takes a row lock inside the caller's transaction, so two simultaneous
creates cannot both take 142.

## Documents

`contract_documents` → `contract_document_versions`, one row per version,
`version_no` never reused.

```sql
CHECK (
  (storage_provider = 'drive' AND drive_document_id IS NOT NULL)
  OR (storage_provider = 'local' AND local_path IS NOT NULL)
)
```
A version with neither a Drive handle nor a local file is a row pointing at
nothing; refusing it here beats discovering it at download time.

```sql
CHECK (contract_id IS NOT NULL OR request_id IS NOT NULL OR amendment_id IS NOT NULL)
```
Every document belongs to exactly one owner record. Without this a row can be
orphaned by a cascade and become invisible but undeletable.

`checksum_sha256` is `CHAR(64)` with a hex `CHECK`. Two versions with the same
hash are the same file — which is how "the counterparty returned it unchanged"
is detected without diffing megabytes of PDF.

## Obligations

`contract_obligations` (the rule) and `obligation_occurrences` (one instance
falling due) are separate so a recurring obligation has a compliance history
rather than a single mutable date.

```sql
UNIQUE (obligation_id, due_date)
```
Makes generation idempotent — re-running never duplicates a due date.

```sql
CHECK (frequency <> 'custom' OR (custom_interval_days IS NOT NULL AND custom_interval_days > 0))
```
A custom frequency with no interval would generate no occurrences and look like a
working obligation that silently never fires.

`last_reminder_days` records the highest ladder band already sent, so a nightly
sweep re-run cannot send the same 7-day warning twice.

## Approvals

`contract_approval_instances.steps_snapshot` freezes the workflow's steps at
submission. A workflow edited mid-approval must not change who was supposed to
approve a contract already in the queue.

`contract_approval_assignments` exists so "my pending approvals" is one indexed
read rather than a workflow replay per contract.

## Risk

```sql
CREATE UNIQUE INDEX uq_risk_assessment_current
  ON contract_risk_assessments (contract_id) WHERE is_current;
```
One current assessment per contract. A stale "current" alongside a fresh one
would make the dashboard's risk counts depend on row order.

The rule table's `subject` and `operator` are `CHECK` enums, so a rule can never
become arbitrary code — the subject names an evaluator branch and the operator
names a comparison.

## The two logs

**`contract_activity_logs`** is the readable story: "Approval requested from
Legal". Trimmable, presentational.

**`contract_audit_logs`** is the compliance record: before and after values, the
actor, their IP. Append-only at the database level —

```sql
CREATE TRIGGER trg_contract_audit_logs_no_update
  BEFORE UPDATE OR DELETE ON contract_audit_logs
  FOR EACH ROW EXECUTE FUNCTION contract_audit_logs_immutable();

REVOKE DELETE ON contract_audit_logs FROM PUBLIC;
```

Merging the two would mean either an unreadable timeline or a mutable audit
trail.

## Notifications

```sql
CREATE UNIQUE INDEX uq_notification_dedupe
  ON contract_notifications (environment, cmp_id, recipient_uuid, dedupe_key)
  WHERE dedupe_key IS NOT NULL;
```

This is what makes the nightly sweeps safe to run twice. cPanel cron is not
exactly-once, and without this a double run tells everyone twice.

## Jobs

`contract_jobs` and `ai_jobs` share their mechanics — status, attempts,
`max_attempts`, `available_at`, `locked_at`, `locked_by`, an idempotency key with
a partial unique index over queued and running rows — and stay separate because
AI work costs money per call, needs more conservative retries, and carries
provider, model and token counts a general job has no use for.

`contract_job_runs` records each cron run against a run key, which is how a
double-scheduled cron becomes a no-op instead of a second round of
notifications.

## Search

```sql
setweight(to_tsvector('english', contract_number), 'A') ||
setweight(to_tsvector('english', title), 'A') ||
setweight(to_tsvector('english', counterparty_name), 'B') ||
setweight(to_tsvector('english', commercial_summary), 'C') ||
setweight(to_tsvector('english', description), 'D') || …
```

Weights order the results: the number and title are what someone is most likely
typing.

Trigram indexes (`pg_trgm`) sit alongside for substring matching, so "acme"
finds "Acme Industries Pvt Ltd" without the user knowing to search whole words.

Extracted document text is indexed **separately**. Folding a 60-page PDF into the
contract's own vector would drown the title and number in every ranking.

No Elasticsearch. The corpus is one company's contract metadata, GIN handles it
comfortably, and a second datastore to deploy, secure and keep in sync would buy
nothing at this size.

## Indexes

197 across the schema, built for the query shapes the product actually uses:

- `(environment, cmp_id, status) WHERE archived_at IS NULL` — the repository list
- `(environment, cmp_id, expiry_date) WHERE archived_at IS NULL` — expiry views
- `(environment, notice_deadline) WHERE notice_deadline IS NOT NULL` — the
  nightly sweep, across tenants
- `(status, due_date) WHERE status IN ('upcoming','due','overdue')` — the
  obligation sweep
- `(queue, status, priority, available_at) WHERE status = 'queued'` — dequeue

Partial indexes throughout: the sweeps care only about open rows, and indexing
the closed ones would cost writes for a read nobody makes.

## Per-company seed data

A company's contract types, clause categories, standard clause wording, template
variables, risk rules and default playbook are **copied into the company** on
first use by `CompanyBootstrapService`, from `Support\SeedCatalog`.

Sharing them from a `cmp_id = 0` row would mean every tenant-scoped query needed
`OR cmp_id = 0`, and every one of those is a place a cross-tenant leak can hide.
Copying costs one write per company and makes the isolation rule absolute: a row
belongs to exactly one company, always. It also lets a company rewrite its
liability clause without that reaching anyone else.

## Testing the schema

`tests/SchemaTest.php` asserts every expected table exists and exercises the
constraints that carry meaning — the status vocabulary, the date ordering,
per-tenant number uniqueness, the audit trigger, the search trigger, the
storage-location rule, the custom-frequency rule, and the one-current-assessment
index.
